Своё Android-приложение: **файрвол + базовый Wireshark**. Выросло из идеи форка PCAPdroid; исходный список идей — `FORK_PROPOSAL.md`.

## 2. Модель правил

### 2.1 Оси
- **Кто:** `Глобально` → `Группа приложений` → `Приложение` (+ системные uid: Unknown, netd/DNS, root, system…).
- **Куда** (от широкого к узкому): `Всё` → `Страна` → `ASN` → `CIDR` → `IP` → `домен` → `поддомен` → … → `точный хост` → *(позже: маршрут/URL-путь, только для расшифрованного трафика)*.
  - Имя точнее IP.
  - Порт и протокол (`tcp/443`, `udp/*`) уточняют любое назначение.

### 2.2 Синтаксис имён
- Свои маски: `*` = любые символы **внутри одного уровня** (не переходит через точку), `**` = любая глубина.
- Флаг **«включая поддомены»** у правила на домен.
- Без regex.
- Маска считается шире точного имени той же глубины.

### 2.3 Наборы правил (rule sets)
- Правило всегда лежит в наборе. Без явного выбора оно попадает в **default** (приоритет 1, самый высокий).
- Наборы включаются и выключаются; порядок значимости меняется **перетаскиванием**.
- Импорт из сторонних форматов создаёт **отдельный набор с минимальным приоритетом**.
- **Профиль** = сохранённый снимок «какие наборы включены и в каком порядке»; переключается одним нажатием, с плитки и через виджет.
- **Условий нет** — ни у правил, ни у наборов: никакой сети/SSID, расписания, экрана/фона. Набор просто включён или выключен; переключение — вручную или профилем. *(решение 2026-11-14)*
- **Временных ограничений нет** совсем: ни временных правил, ни «разблокировать на N минут», ни расписаний.

### 2.4 Режим работы
- Один режим: **всё разрешено, кроме того, что запрещено правилами.** Режим whitelist («всё запрещено») убран *(решение 2026-11-14)*.
- «Запретить приложению всё» — обычное правило приложения с типом «Всё» (создаётся через «+ правило»); отдельной «политики в наборе» в интерфейсе нет.
- Никаких самостоятельных блокировок: без правил трафик не трогается. Нет «блокировать новые приложения», нет режима «спросить».

### 2.5 Алгоритм решения
1. Наборы перебираются по приоритету (1 → N), только включённые. **Первый набор, давший решение, побеждает.**
2. Внутри набора сначала правила приложения (приложение → его группы), потом глобальные. Побеждает самое узкое «куда»; при равенстве — блокировка.
3. Политика приложения «всё разрешить / всё запретить» — обычное правило «приложение → всё» внутри набора.
4. Глобальное **разрешение** только снимает глобальные блокировки; оно не открывает то, что приложению запрещено в каком-либо наборе (поиск продолжается по нижним наборам только среди правил приложения).
5. Решения нет → соединение разрешено.
6. В соединении хранится id сработавшего правила, его набор и профиль, чтобы показать «почему заблокировано».

### 2.6 Действие блокировки
- По умолчанию **drop**, как сейчас; у правила и набора можно выбрать **reject**: TCP RST / ICMP unreachable / DNS NXDOMAIN.
- DNS-запрос к заблокированному домену получает подменённый ответ.
- Если имя заранее неизвестно (общий IP), соединение ждёт ClientHello и решение принимается по SNI.

### 2.7 DNS
- Встроенный DoH/DoT к выбранному серверу (AdGuard, Quad9, Cloudflare, свой). Системный «Частный DNS» можно выключить и при этом видеть имена.
- Блокировка на уровне DNS для заблокированных доменов.

## 2.8 Upstream-цепочка (вариант A, решение 2026-11-15)
Packetwall остаётся VPN-файрволом, но разрешённый трафик может уходить не напрямую, а в локальный или удалённый прокси (например sing-box, v2rayNG, FlClash в режиме «только прокси», без своего VPN).
- **Протоколы:** SOCKS5 (TCP + UDP через UDP ASSOCIATE) и HTTP CONNECT (только TCP). Хост, порт, логин и пароль.
- **Приложение-прокси** исключается из VPN Packetwall (`addDisallowedApplication`), чтобы его исходящий трафик не возвращался в петлю; собственные сокеты Packetwall защищаются `VpnService.protect()`.
- **UDP/QUIC через upstream** — включается отдельно (для HTTP CONNECT невозможно: UDP идёт напрямую).
- **DNS через upstream** — встроенный DoH не уходит мимо прокси.
- **Если upstream недоступен:** блокировать (kill switch) или пускать напрямую.
- **Проверка соединения:** задержка, внешний IP, работает ли UDP.
- Фильтрация, логи и анализ пакетов работают до отправки в upstream, поэтому ничего не теряется. В обзоре соединения есть поле «Маршрут».
- Реализация опирается на уже имеющуюся в `zdtun` пересылку соединений в SOCKS5.
- **Позже:** маршрут как действие правила (разрешить напрямую / через upstream), встроенный WireGuard или ядро sing-box.

## 3. Импорт / экспорт / фильтры
- **Фильтры (подписки):** набор привязан к URL списка, автообновление по расписанию (можно только по Wi-Fi), встроенный каталог (HaGeZi, OISD, AdGuard, RU-списки), свои URL. Вкладка «Фильтры», выключатели, «Обновить все».
- **Импорт:** окно выбора исходного формата → конвертация в свой формат с отчётом о пропущенном. Форматы:
  - hosts, простые списки доменов, CIDR-списки;
  - сетевые правила uBO/AdGuard (`||x^` → домен с поддоменами, `@@` → разрешение, `$app=` → приложение, `$important` → наверх набора; остальное — в отчёт);
  - экспорты PCAPdroid, NetGuard, AFWall+, RethinkDNS, sing-box rule-set.
- **Экспорт:** свой JSON (версионированный, без потерь), hosts, список доменов, CSV; весь набор / профиль / выбранное.
- **Автобэкап** правил и настроек в выбранную папку по расписанию.

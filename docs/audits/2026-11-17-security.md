# Packetwall security audit (read-only, HEAD 653aa36)

I read the docs, both manifests, the engine and fw packages, and the native diffs since `be085d8` (`pw_rules.c`, `capture_vpn.c`, `pcapdroid.c`, `jni_impl.c`, `pcap_dump.c`) plus the zdtun patch. The rest of the Kotlin surface was covered too: Streaming, DnsProxy, ListParser/ListSource, ForeignImport/RethinkReader, MmdbReader/GeoIp, Dissector/TlsInfo/PacketStore, SecretBox/Settings, LogDb, tile, widget, notification and Schedules. One memory and CPU claim was confirmed with a standalone C harness in /tmp/claude-1000/pwaudit, which compiles the matcher functions copied out of `pw_rules.c`. Nothing in the repository was changed.

## HIGH

**H1. Any app can turn the firewall off.** `AndroidManifest.xml:24-26` exports `MainActivity`, and `MainActivity.kt:54-65` acts on the `TOGGLE_OFF` action (calls `CaptureService.stop`).
- **Trigger:** any app on the device that is in the foreground (background activity starts are restricted, foreground ones are not).
- **Exploit:** `startActivity(Intent("io.github.cinnamon415.packetwall.TOGGLE_OFF").setClassName("io.github.cinnamon415.packetwall", "io.github.cinnamon415.packetwall.MainActivity"))`, then immediately bring its own activity back to the front.
- **Impact:** protection stops and all traffic leaves unfiltered, including through the proxy kill switch. The only visible sign is a brief flash of the app and the VPN key icon disappearing.
- **Confidence:** confirmed.
- **Fix:** take intent-action handling out of the exported launcher activity. The tile and widget already use explicit same-app PendingIntents, so they can target a non-exported trampoline activity (`exported=false`). Drop `TOGGLE_OFF` entirely; e2e can use the debug-only component.

**H2. The pcap-over-IP server has no authentication.**
- **Where:** `analysis/Streaming.kt:76` opens `ServerSocket(port, 4, lan ? null : 127.0.0.1)` and streams every captured packet to whoever connects. There is no token and no peer check.
- **Trigger, local (default):** any app with INTERNET permission. Loopback traffic does not pass through the VPN, so the firewall cannot stop it. Connecting to 127.0.0.1:57012 gives it a full packet sniffer of all apps: plaintext HTTP including cookies and tokens, DNS, SNI, and per-packet uid comments. This breaks the Android app sandbox whenever "stream" is on.
- **Trigger, "allow LAN":** binding to `null` means `::` on every interface, including Wi-Fi on public hotspots and cellular IPv6 on carriers that allow inbound traffic. Anyone who can reach the port gets all traffic. That is critical for this option; the existing UI warning only mentions the local network.
- **Side DoS:** the server accepts unlimited clients, each with a queue of up to 4096 blocks (`Streaming.kt:39`). A local app that opens many connections and never reads can OOM the process, which also hosts the VPN.
- **Confidence:** confirmed.
- **Fix:**
  - Default mode: use a `LocalServerSocket` (abstract namespace; `adb forward tcp:57012 localabstract:packetwall-pcap` works) and accept only peers whose `getPeerCredentials().uid` is 2000 (shell) or 0.
  - LAN mode: require a random token as the first line, bind to the Wi-Fi interface address only, and cap the number of clients.

**H3. The upstream kill switch fails open when the proxy host cannot be resolved at start.**
- **Where:** `CaptureService.kt:81-82` sets `upstreamIp = resolve(upHost)`; on failure it only shows a toast. `NativeBridge.kt:117` then reports `getSocks5Enabled() = upstreamIp != null`, i.e. 0, and `CaptureService.kt:112-115` sets the state to active with no relay.
- **Trigger:** a DNS hiccup or no network at VPN start (boot, tile, widget, START_STICKY restart) while the proxy is configured by hostname.
- **Impact:** the VPN runs with no upstream at all. All TCP, UDP and DNS go direct for the whole session even though "kill switch" is selected, and the proxy app is not excluded either. In `wants_upstream()` (`capture_vpn.c:419`) the `!pd->socks5.enabled` check goes straight to direct.
- **Confidence:** confirmed.
- **Fix:** when `st.upstream && upOnDown == KILL` and resolution fails, start in a block-all state: set the proxy to an unroutable address, or add a native `upstream_failed` flag that blocks every non-VPN-DNS flow. Keep re-resolving in `UpstreamMonitor`. Also take the 4-second resolve off the main thread.

**H4. DNS leaks around the upstream proxy, and DNS keeps flowing while the kill switch is engaged.**
- **Plain DNS:** in system-DNS mode, queries to the VPN DNS are DNAT'd to the network resolver. The UDP relay and UDP-block branches explicitly exclude `internal_dns` (`capture_vpn.c:627-635`), so every query goes to the ISP or hotspot resolver in cleartext from the real IP. This holds even with "all through upstream", UDP=proxy and kill switch on with the proxy down.
- **DoH:** `CaptureService.kt:132` routes DoH directly, not through the proxy, whenever SOCKS5 has a login. The DoH provider sees the real IP and every name.
- **IPv6 fallback DNS:** `VpnSetup.kt:48` adds Quad9 (`2620:fe::10`) whenever DoH is off, so part of the queries silently go to a resolver the user did not choose.
- **Trigger:** the network operator, a passive observer, or the DoH provider.
- **Impact:** browsing names are revealed despite the proxy chain, which defeats spec 2.8 ("DNS через upstream").
- **Confidence:** confirmed.
- **Fix:**
  - While the upstream is wanted, send VPN DNS through the relay (UDP proxy mode) or force DoH through the proxy.
  - OkHttp cannot do SOCKS5 authentication; for that case, resolve via DNS-over-TCP through zdtun's own SOCKS connection, or refuse DoH-direct and block.
  - Under kill switch with the proxy down, block DNS too.
  - Make the Quad9 IPv6 fallback opt-in.

## MEDIUM

**M1. IPv6 routes cover only `2000::/3` and `fc00::/7` (`VpnSetup.kt:35,37`).**
- **Gap:** NAT64 prefixes such as `64:ff9b::/96` and `64:ff9b:1::/48` are not in the VPN routes. Android sends a split-tunnel VPN's unrouted destinations over the underlying network; the LAN-bypass feature relies on exactly this behaviour.
- **Trigger:** an app on any NAT64 network (common on mobile carriers and IPv6-only Wi-Fi). It connects to `64:ff9b::<IPv4>` directly, or uses a DNS64 resolver.
- **Impact:** a complete bypass of the firewall, logging and the proxy kill switch.
- **Confidence:** likely; it rests on the same routing fall-through the LAN bypass depends on.
- **Fix:** `addRoute("::", 0)`. With LAN bypass, subtract `fe80::/10`, `fc00::/7` and `ff00::/8` the same way `Routes.subtract` already does for IPv4.

**M2. Exponential `**` matching freezes the capture thread.**
- **Where:** `pw_rules.c:201-213` (`match_labels`; `**` recursion × subdomain loop at `:234-239`).
- **How a list gets there:** `ListParser.domainRe` (`ListParser.kt:26`) accepts `**` as any label. `@@||**.**.**….zz^` or a plain `**.**.…x.com` therefore ends up as a wildcard rule.
- **Measured** with the harness: a pattern of 12 × `**` plus `zz` against a 38-label, 79-character host (nDPI keeps up to 79 characters) took **56 s for one evaluation**; 14 × `**` ran past 100 s.
- **Trigger:** a malicious or compromised list, or an import, plus any host with many labels. A web page can trigger a lookup of `a.a.a…com`.
- **Impact:** `pw_engine_eval` runs on the capture thread, so all device traffic stalls (DoS).
- **Confidence:** confirmed.
- **Fix:**
  - Rewrite the label matcher as an iterative two-pointer or DP matcher, O(p·h).
  - Reject patterns with more than one `**` (or a leading-only `**`) in both ListParser and the engine.
  - Cap labels per pattern.

**M3. DNS-cache poisoning turns a domain allow into an IP, country or ASN bypass.**
- **Where:** `pcapdroid.c:870-937` (`process_dns_reply`) caches ip → query name from any DNS reply nDPI sees, from any server and any uid, into one global LRU. It does not check the answer name against the query. `pcapdroid.c:611` then labels new connections with that cached name, and in the engine a domain rule outranks IP, country and ASN rules.
- **Trigger:** a malicious app, or a colluding unrestricted app.
- **Exploit:** the app sends its own UDP/53 query `www.google.com` to a server it controls. The server answers A = `<blocked IP>`, for example an address in a blocked country or ASN. The app then connects to that IP; the connection carries host `www.google.com`, the user's allow `*.google.com` wins, and the connection is allowed. The later SNI does not re-block it, because the SNI also says google.com or is absent.
- **Confidence:** confirmed code path.
- **Fix:**
  - Populate the cache only from replies of the VPN DNS / DoH path (`internal_dns`), or key the cache by uid.
  - Require that the answer RR names match the query (or its CNAME chain).
  - Do not let a domain allow override an IP-class block when the name came only from the LRU (`info_from_lru`).

**M4. Silent truncation of the candidate list (`MAX_CANDIDATES 256`, `pw_rules.c:44,562-565`, used at `:629-658`).**
- **How:** extra matching rules are dropped without notice. Literal candidates are added first, then linear ones in insertion order.
- **Exploit:** a list with more than 256 distinct wildcard allow entries that each match every host (e.g. `@@||**.*.c*m^`, `@@||**.*.co*^`, …) fills the array for every `.com` host. Linear rules added later never become candidates, including app "block all" rules, IP/CIDR, country and ASN rules in lower sets. A list allow can normally only cancel global blocks; this neutralises app rules as well.
- **Trigger:** a malicious or compromised list.
- **Confidence:** likely (reasoned from the code, not run).
- **Fix:** do not collect candidates. Keep a running best per (set, who) while scanning, or use a dynamic array.

**M5. Native debug logging of every hostname is on in release builds.**
- **Where:** `common/utils.c:29` sets `loglevel = 0` and nothing ever calls `set_log_level`. Every `log_d` therefore reaches logcat, including:
  - `pcapdroid.c:614` "Host LRU cache HIT: ip -> host";
  - `pcapdroid.c:936` "Host LRU cache ADD … -> query";
  - netd uid resolutions, spoofed replies and similar.
- **Trigger:** adb and bug reports (shared with OEMs and developers), or apps granted READ_LOGS.
- **Impact:** a full browsing history in logcat, plus per-packet logging overhead.
- **Confidence:** confirmed.
- **Fix:** `set_log_level(BuildConfig.DEBUG ? ANDROID_LOG_DEBUG : ANDROID_LOG_WARN)` at loop start, and keep hosts out of warn-level messages.

**M6. A malicious list server can OOM the process that hosts the VPN (fail-open).**
- **Where:** `FirewallStore.kt:363-365` limits lines only (`MAX_LIST_LINES = 3_000_000`), not line length or total bytes. One endless line or around 1 GB of long lines exhausts the heap. The same applies to:
  - imports, which `readBytes()` the whole file (`SetsScreens.kt:327`);
  - the RethinkDNS zip entry, copied unbounded to disk (`RethinkReader.kt:17`);
  - the GeoIP gzip, which is also unbounded (`GeoIp.kt:170`).
- **Trigger:** a compromised or malicious list host. HTTPS is enforced, because the default network-security policy blocks cleartext.
- **Impact:** UI, worker and VPN share one process, so the OOM kills the VPN. Without lockdown, traffic flows unfiltered until the START_STICKY restart, and the daily worker retries, causing repeated crashes. Any other crash in the UI has the same effect.
- **Confidence:** likely.
- **Fix:**
  - Cap the byte count and the line length (for example a 4 KB line cap in a custom reader, 200 MB total).
  - Move `CaptureService` to its own process (`android:process=":vpn"`).
  - Tell users to enable Always-on VPN with "Block connections without VPN".

**M7. App and group rules are compiled to uids once; package changes do not trigger a recompile.**
- **Where:** `RulesCompiler.kt:51-52`. There is no PACKAGE_ADDED, REMOVED or REPLACED receiver anywhere.
- **Effect while the VPN runs:**
  - A newly installed app with pre-existing rules (imported, or reinstalled with a new uid) is unfiltered until the next compile.
  - Android reuses freed app IDs, so a new app can inherit an uninstalled app's allow or route rules.
  - Logs mis-attribute uids.
- **Confidence:** likely.
- **Fix:** register a package-change receiver (dynamic, in the service) that calls `scheduleCompile()` and clears the AppsResolver cache.

## LOW

- **L1. The DoH proxy is an open local resolver.** `DnsProxy.kt:54` binds UDP 127.0.0.1 on a random port, readable from `/proc/net/udp`.
  - Any app can resolve through it directly, which skips Packetwall's DNS-level blocking and uses the user's proxy (HTTP with login).
  - Flooding the 8-thread, 256-slot pool causes SERVFAIL for the whole device.
  - Fix: verify the sender port belongs to the engine's DNAT socket, or have the engine call the resolver in-process, or use a socketpair.
- **L2. Domain rules are advisory against an adversarial app.**
  - With app-side DoH (allowed by design, `capture_vpn.c` blocks only port 853) the SYN is allowed with no name. With ECH the real SNI never appears.
  - Names are not normalised: `pw_match_domain` / `split_labels` treat `blocked.com.` (trailing dot in SNI or HTTP Host) as a different name, so literal and wildcard rules miss it.
  - Note: nDPI truncation keeps the tail (`ndpi_main.c:12935`), so long names do not bypass suffix rules.
  - Fix: strip one trailing dot in `pw_engine_eval`, and offer a built-in "block DoH resolvers / HTTPS-RR (type 65)" set.
- **L3. Silent fail-open on rule problems.**
  - `compileNow` sets `_loaded = -1` (`FirewallStore.kt:540-548`) but no screen shows it.
  - A missing list file is simply skipped (`RulesCompiler.kt:69`; `pw_rules.c` only `log_w`s), and invalid lines are dropped.
  - If the first compile after process start fails, the engine is empty while protection shows as on.
  - The rules file itself is written atomically (`tmp` + `renameTo`), and `pw_fw_load` keeps the old engine on fopen/OOM failure, so a half-written file is not a real risk.
  - Fix: surface load errors and count missing lists on the Home screen.
- **L4. Unseeded FNV-1a with linear probing** (`pw_rules.c:82,111-130`). A crafted list of keys that collide in the low bits makes loading O(n²) and slows lookups on the capture thread. `startCapture` runs `compileNow()` on the main thread, so the result is an ANR and protection cannot start. Fix: a seeded hash (SipHash or a random seed) and a cap on probe length.
- **L5. Proxy credentials are truncated natively.** `jni_impl.c:579-593` uses a `buf[64]` and `pcapdroid.h:292-293` keeps user and password at 31 characters each; the split is on the first `:`. A longer password fails TCP authentication (fail-closed) while `UdpAssociation` uses the full value. The password never leaks: logging is commented out, it is not in exports or backups, and it is sealed with AES-GCM via SecretBox. It stays plaintext in memory, which is expected. Fix: 256-byte fields, pass user and password as separate JNI getters, and validate lengths in the UI.
- **L6. zdtun patch: fail-open design and unordered shared state.**
  - `zdtun.c:1650-1653` sends a relay-marked UDP flow direct if the relay vanished before its first packet. That is unreachable today, because the mark and the forward happen in the same loop pass, but it should drop instead.
  - `zdtun.c:2054` reads `payload_ptr[4]` when `l4_len == 4`; this is a stale in-buffer read and harmless, but check `l4_len >= 5` first.
  - The `udp_relay_*` and `upstream_*` globals are written from Java threads with no memory barrier (`jni_impl.c` setUdpRelay; `volatile` gives no ordering on arm64), so a torn ip/port pair is possible. Use a mutex or a single atomic struct swap.
  - HTTP CONNECT parsing and building are bounds-safe: the request is at most ~505 of 768 bytes, base64 fits in 400, and `atoi` over-read stays inside the 64 KB `reply_buf`. Bytes after the header end are discarded, which is a correctness bug, not a security one.
- **L7. Imported Packetwall JSON auto-fetches subscription URLs without confirmation and refreshes them daily** (`FirewallStore.kt:523`). A shared ruleset gives its author a persistent content channel (enabling M2, M4 and L4) plus a daily ping with the user's real IP: Packetwall is excluded from the VPN and the proxy. Fix: show the URLs and ask before downloading.
- **L8. Backup and storage.** `allowBackup=false` does not stop device-to-device transfer for targetSdk ≥ 31, so `log.db` (full URLs and hosts), captures and rules would migrate. Add `dataExtractionRules` excluding everything. `LogDb.clear` leaves data in SQLite free pages; use `PRAGMA secure_delete=ON` or VACUUM.
- **L9. Untrusted SQLite and XML in imports.** The RethinkDNS `.rbk` is opened as SQLite and the NetGuard XML goes through the default `DocumentBuilderFactory`. Both are user-chosen files, there is no zip-slip (the file name is fixed), and Android's parser does not fetch external entities. Remaining risk is crashes, which kill the VPN as in M6. Disable DOCTYPE in the XML parser, size-cap the inputs, and wrap imports in `catch (Throwable)`.
- **L10. MMDB parsing.** `MmdbReader` is pure JVM, so there is no memory corruption. A pointer loop in a hostile DB, however, throws `StackOverflowError`, which `GeoIp.country`'s `catch (e: Exception)` does not catch, inside a JNI callback on the capture thread. The source is db-ip.com over HTTPS. Fix: catch `Throwable` and bound pointer depth.
- **L11. ICMP is never proxied**, so pings reveal the real IP when "all through upstream" is set.

## Checked and found OK

- `TestConfigActivity` exists only in `src/debug` and is merged only into the `.debug` variant, so it cannot ship in release. Do not run the debug APK as a daily driver: it lets any app replace the rules and settings, including the upstream host.
- The tile is protected by `BIND_QUICK_SETTINGS_TILE`. Widget and notification PendingIntents are explicit and immutable. The widget receiver and `CaptureService` are not exported. There is no boot receiver. WorkManager components are permission-protected.
- No cleartext: there is no network-security config and targetSdk is 37, so the http downgrade in the `ListSource` redirect code is blocked by the platform.
- `pw_rules.c` file parsing is bounds-safe: `strncpy`, fixed buffers, a field-count check, and `fgets` splitting only produces invalid lines. `ip_in_cidr` and the mask maths are correct.
- `send_tcp_rst`, `spoof_dns_reply` and the pcapng "dropped" option are sized correctly. The rules hot swap is properly locked, and the capture thread alone frees the old engine.
- `Dissector`, `TlsInfo` and `PacketStore.keyOf` are bounds-checked.
- `RulesCompiler.sanitize` strips tab, CR and LF, so field or line injection into `rules.compiled` is not possible.
- R8 keep rules (`engine.**`) are fine. The dependencies are recent (OkHttp 4.12.0, work 2.10.1, Compose BOM 2025.05.01) with no known-vulnerable pins.

## Top 5 fixes

1. Remove `TOGGLE_ON`/`TOGGLE_OFF` handling from the exported `MainActivity` and use a non-exported trampoline (H1).
2. Make the upstream fail closed: block everything when the proxy host cannot be resolved, route DNS through the upstream or block it, and stop DoH bypassing a SOCKS5 proxy with a login (H3, H4).
3. Put authentication on pcap-over-IP: an abstract `LocalServerSocket` with a peer-uid check for adb, and a token plus Wi-Fi-only bind plus a client cap for LAN (H2).
4. Route IPv6 `::/0`, subtracting only the local prefixes, to close the NAT64 bypass (M1). Run the VPN in its own process and recommend Always-on with lockdown, so crashes and OOMs do not fail open (M6).
5. Harden the rule engine against hostile lists and apps:
   - a linear-time `**` matcher and a `**` limit in ListParser (M2);
   - no candidate cap (M4);
   - DNS-cache entries only from the VPN resolver, keyed by uid (M3);
   - a seeded hash (L4);
   - in the same pass, set the release native log level to WARN (M5).
